# How HY4 Flash turns a prompt into an answer on one DGX Spark

## How the model works

### From text to a prediction

Suppose you send “The parcel is at the station. Which place was mentioned?” The tokenizer splits the question and its chat markers into pieces called tokens. A piece can be a whole word, part of a word, punctuation, or a control marker. The tokenizer replaces each piece with an integer. HY4 Flash looks up a row in its embedding table for each integer. Every row starts as a list of 3,072 learned numbers, with the same row available whenever that piece occurs. The values computed from those rows will change as the model reads this particular question. The stored embedding and other trained matrices are **weights**, while the question-dependent vectors and saved attention history are **request state**. [Tencent model and configuration](https://huggingface.co/tencent/Hy4-flash/tree/b2498eba6a1a3f9bbcab4190bc1313a3c7010c2f)

The decoder transforms each position through 42 blocks. Each block needs to combine two kinds of work. Attention gathers information across positions, including the relevant “station” mention. The feed-forward network rewrites features for one position. The first block uses a dense feed-forward network. The next 41 blocks use a mixture of experts. After the last block, the output head produces a score for each of 120,832 vocabulary entries. A score before conversion to probability is called a **logit**. The sampler can pick the highest score or draw from eligible scores after applying temperature, top-k or top-p. The accepted ID becomes input for the next prediction, and the engine turns accepted IDs into text as the reply streams. [Architecture specification](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction)

### How short and long attention work together

A position creates a **query** that can match other positions’ **keys**. The corresponding **values** carry information toward the current position. When attention selects positions related to the question, their values contribute more strongly to the result. The causal mask restricts a position to information that was available when it appeared. During generation the engine saves attention data so it can continue without replaying the entire document every time it adds a token.

HY4 Flash starts with two sparse-attention blocks. The remaining 40 alternate groups of three sliding-window blocks and one sparse block. Across the stack, 30 blocks read the most recent 512 visible positions and 12 can select relevant groups from the wider history. The sliding window provides direct access to nearby word order and syntax. The sparse path can select a distant paragraph containing “station” even when that paragraph has left the sliding window. The IndexPool indexer scores a compact description of groups, then the main attention reads the eligible original positions in the selected groups. Tencent describes a capacity of up to 2,048 selected positions. The released CUDA patch also defines the handling of the tail group and its causal mask. A relevant group can be missed, so context capacity alone does not establish retrieval reliability. [Tencent attention design](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction) · [Pinned CUDA patch](https://huggingface.co/AngelSlim/Hy4-flash-GGUF/blob/bcbc7db5dcf4162cc1e1b8ed6c65567e843ebe46/patch/hy4-flash-spark.patch)

These blocks use **multi-head latent attention**, or MLA. A head learns a way of matching positions. Saving every key and value for every head would add up over a long document. MLA learns a smaller intermediate representation for earlier positions. The model can perform the corresponding projections during attention so the cache can retain a compressed latent and positional features in place of independent full-size head tensors. The released model reports a KV latent rank of 512. The exact runtime footprint also depends on the sliding-window buffers, sparse indexer rows, packing, cache precision and number of slots. [Model dimensions](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction) · [Pinned CUDA patch](https://huggingface.co/AngelSlim/Hy4-flash-GGUF/blob/bcbc7db5dcf4162cc1e1b8ed6c65567e843ebe46/patch/hy4-flash-spark.patch)

### The model chooses which weights to read

In an expert block the router scores 512 possible expert networks and selects 16 for the current position. These are learned functions. Their outputs are weighted and combined. Another shared expert runs alongside the routed path. HY4 Flash makes the routed path smaller by projecting its input from width 3,072 to 1,536 before the selected experts transform it. It projects the result back into the decoder’s working width. The router still sees the full-width input. Because a later position can choose a different set of experts, the server has to keep all the required weights available even though any one position reads a fraction of them. The model card reports 155.5 billion backbone parameters and 11.3 billion text-active parameters per token. Its roughly 220 billion headline total includes the Engram tables and other components. [Tencent model breakdown](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction) · [Routed and shared expert implementation](https://huggingface.co/AngelSlim/Hy4-flash-GGUF/blob/bcbc7db5dcf4162cc1e1b8ed6c65567e843ebe46/patch/hy4-flash-spark.patch)

**Identity Hyper-Connections** preserve four residual streams through the stack. An update can read a learned combination of the streams and add a contribution back, while the identity path carries earlier features forward. These streams belong to one position. They let successive sublayers combine information at different depths of one request.

**Engram** adds phrase features at layer indices 1, 11, 21 and 31. Suppose “the station” occupies two tokens. Their IDs can be hashed together to retrieve features associated with the two-token combination. An adjacent three-token sequence forms another address. For each of the two sequence lengths, eight hashes address learned feature tables. The retrieved vectors join the position’s evolving activations. The tables add around 64 billion parameters. Looking up a phrase typically needs a few rows, making it possible to map the table from disk and read selected pages as needed. These lookups are part of the model. The attention cache is generated independently for the current request. [Architecture and Engram dimensions](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction) · [Engram research](https://arxiv.org/abs/2601.07372)

### Images and speculative generation

The upstream model also takes images. A SigLIP2-derived encoder divides the pixels into patches, processes them with a 27-layer vision transformer, and merges neighboring features. A learned projector maps the visual features into the language decoder’s width so the same text generator can answer a question about the image. The launcher here is designed for the text-only performance pass. Image tests require the matching projector file and their own evidence. [Upstream vision configuration](https://github.com/Tencent-Hunyuan/Hy4-flash#model-introduction)

Tencent packages a small five-layer DFly2 drafter with the original model. A drafter proposes likely continuations that the main model can check together. When several pass verification, one main-model forward can advance the answer by several tokens. A rejected proposal cuts off that candidate suffix. The Spark GGUF launcher selects the patched engine’s `draft-mtp` route, as AngelSlim documents. Report its measured draft depth and accepted proposals from the logs. The official vLLM and SGLang examples select their `DFLY` implementation, so their measured acceptance and speed belong to those launches. [Tencent drafter notes](https://github.com/Tencent-Hunyuan/Hy4-flash#dfly2-for-speculative-decoding) · [AngelSlim Spark launch](https://huggingface.co/AngelSlim/Hy4-flash-GGUF/blob/bcbc7db5dcf4162cc1e1b8ed6c65567e843ebe46/README_SPARK-4Bit.md)

## How this recipe runs it on one DGX Spark

The Spark’s GB10 GPU and Grace CPU share one pool of physical memory. Putting a tensor on the CPU does not create an extra pool. The Spark GGUF weighs more than the physical memory when measured as a full disk file. The launcher memory-maps the file and directs `per_layer_token_embd.weight` to the CPU, where the Engram table can be accessed a few rows at a time. The OS can reclaim cold file-backed pages and fault in another page from SSD when a token needs it. The token embedding and most compute weights go to the GPU path. Disk-space requirements, GPU-reported allocation, page cache and total host headroom are therefore distinct measurements. [DGX Spark hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html) · [Publisher placement and memory notes](https://huggingface.co/AngelSlim/Hy4-flash-GGUF/blob/bcbc7db5dcf4162cc1e1b8ed6c65567e843ebe46/README_SPARK-4Bit.md)

The build pins llama.cpp and the release patch and targets `121a`, the CUDA architecture for GB10. The two checkpoint choices set different weight representations. Both Spark variants use mixed precision, so “4-bit” should not be read as a uniform four bits for every tensor. The Fast artifact is about 2.7 GiB smaller. Its performance and output agreement need to be measured independently. F16 KV is a separate runtime setting, applied to the generated attention history. [Checkpoint notes](https://huggingface.co/AngelSlim/Hy4-flash-GGUF) · [Launcher](../bin/recipe.sh)

When the loopback server receives a completion request, **prefill** runs the prompt’s known positions and builds its attention state. The launcher lets the engine process chunks of multiple positions together. Time to first token includes that work and request overhead. During **decode**, accepted tokens extend the sequence. MTP can reduce the number of full target evaluations per emitted token, while the length and pattern of the output can change acceptance. A repeated prompt may also reuse cached work. Cold prefill should record zero reusable input positions where the engine exposes that count. Use a real tokenizer and a retrieval answer to confirm a nominal 32K or 128K prompt was actually read.

A startup setting of 196,608 positions and one slot comes from the publisher. A run with more slots has to report each slot’s actual context capacity, the memory state, and whether requests truly ran together. Long prompt retrieval and short simultaneous replies are separate workloads. The benchmark’s throughput and the wall time from sending a message to completing it answer different questions.
